# Лабораторна №3 — підготовка до захисту (5 хв)

**Тема:** Рейтинг і модель об'єктів: dunder-методи, протоколи, декоратори.
**Проєкт:** findex, той самий репозиторій і корпус документації Python 3.13.

## Виступ своїми словами

У лабораторній №3 я продовжив проєкт findex, який почав у першій
лабораторній. Корпус залишився тим самим — офіційна документація Python,
приблизно 514 текстових документів.

Спочатку я створив клас Index навколо інвертованого індексу з лаби №2.
Він підтримує звичайні для Python операції: len(index), перевірку
"python" in index, звернення index["python"], перебір через for,
а також repr(index). Через property отримуємо кількість документів,
а cached_property один раз обчислює середню довжину документа.
Індекс відкривається через with open_index(), після завершення роботи
його кеш і внутрішні структури очищаються навіть у разі винятку.

Далі я реалізував два способи ранжування — TF-IDF та BM25. Обидва
відповідають одному протоколу Scorer, тому можна передати будь-який
із них у функцію пошуку без зміни логіки. BM25 враховує рідкість
слова, насичення частоти та довжину документа. Найкращі k результатів
обираються через heapq.nlargest, а SearchResult можна сортувати,
оскільки це order=True dataclass.

У третій частині я написав рекурсивний парсер для AND, OR, NOT, дужок
і фраз у подвійних лапках. Результат парсингу — дерево об'єктів
Term, Phrase, And, Or, Not. Вони підтримують оператори &, |, ~.
Фрази перевіряються за позиціями слів, тому я будую позиційний
індекс із прапорцем --positions (база для цього була у лабі №2).

Наприкінці я додав декоратор @timed із functools.wraps, кешування
повторних запитів через lru_cache, виділення знайдених слів у сніпетах
і оцінювання результатів за precision@5 на десяти тематичних запитах.
Числа precision@5 у фінальному README беруться з запуску програми
на корпусі, а не з вигаданих прикладів.

У GitHub зберігаються код, тести й документація; коли всі перевірки
та вимірювання готові, створюється тег lab-03.

## Що показати в терміналі VS Code

1. uv run pytest -q
2. uv run ruff check .
3. uv run python -m findex.ranked build data/python_docs --out index-lab03.bin
4. uv run python -m findex.ranked search index-lab03.bin 'python AND (async OR await) NOT java "event loop"' --corpus data/python_docs --repeat 2
5. uv run python -m findex.ranked sanity index-lab03.bin --corpus data/python_docs
6. uv run python -m findex.ranked evaluate index-lab03.bin --corpus data/python_docs

У Windows PowerShell зовнішні одинарні лапки зберігають подвійні
лапки всередині фрази "event loop".

Зверніть увагу на рядки query-cache MISS, а потім query-cache HIT,
і на повідомлення @timed із мілісекундами. У сніпетах знайдені
слова відображаються у вигляді [[word]].

## Відповіді на Reflection

**1. Що роблять dunder-методи?** len(x) викликає __len__, оператор
in — __contains__, індексація — __getitem__. Це протоколи Python,
завдяки яким власні класи поводяться як вбудовані. Краще писати
len(index), а не напряму index.__len__().

**2. Protocol і ABC?** typing.Protocol задає структурний контракт:
достатньо мати потрібні методи. ABC зазвичай вимагає успадкування
або реєстрації. Scorer реалізований через Protocol, щоб TfIdf і BM25
можна було міняти незалежно.

**3. Як працює @timed?** Декоратор повертає функцію-обгортку.
Усередині за допомогою perf_counter вимірюється час, а finally
забезпечує лог навіть під час винятку. functools.wraps зберігає
оригінальні __name__, __doc__ і метадані.

**4. Декоратор з аргументами?** Додається ще один рівень замикання:
retry(times) повертає decorator(func), а той — wrapper(*args, **kwargs).

**5. Context manager і yield?** У @contextmanager код до yield
виконується під час __enter__, після yield — під час __exit__.
Блок finally виконується навіть у разі помилки чи return всередині with.

**6. Чим BM25 відрізняється від TF-IDF?** BM25 насичує частоту терміна:
додаткові повторення дають дедалі менше балів. Також він нормалізує
частоту довжиною документа. k1 визначає силу насичення, b — силу
нормалізації довжини; якщо b=0, довжина не впливає.

**7. Навіщо heapq.nlargest?** Для n документів і малого k
пошук k найбільших значень займає приблизно O(n log k),
тоді як повне сортування — O(n log n). Для топ-5 heap вигідний.

**8. Чому a OR b c = Or(a, And(b,c))?** У граматиці AND має
вищий пріоритет за OR, тому спочатку об'єднуються b і c.
Тести перевіряють саме структуру AST, не лише текст дерева.
