# Лабораторна №6 — захист (5 хвилин)

**Тема:** Асинхронний краулер: asyncio. Проєкт findex 0.6.0.

## План демонстрації

1. Запустити власний сервер документації (у першому терміналі):

       uv run python -m findex.lab06_mirror serve

2. У другому терміналі показати живі лічильники:

       uv run findex crawl http://127.0.0.1:8765/ --max-pages 200 --concurrency 20 --per-host 10 --delay 0.001 --out data/crawl.jsonl --log crawl.log --debug

3. Після завершення окремо побудувати індекс і виконати пошук:

       uv run findex index data/crawl.jsonl --out index-lab06.bin --positions
       uv run findex search index-lab06.bin "python OR asyncio" --corpus data/crawl.jsonl --k 5

4. Показати таблицю реальних вимірювань у README, рядки 429/retry/200
   у журналі, JSONL та результати пошуку. Зупинити сервер Ctrl+C.

## Виступ своїми словами

У цій лабораторній я додав асинхронний краулер до findex.
Для експерименту використовую власне локальне дзеркало
документації Python: 200 сторінок із матеріалів попередньої
лабораторної. Я сам запускаю сервер, він дозволяє обхід у robots.txt,
крім /private. User-Agent містить посилання на Issues мого репозиторію.

Краулер має одну чергу URL і TaskGroup із кількома воркерами.
Кожен воркер чекає HTTP-відповідь через await; поки він чекає,
event loop виконує інші готові корутини. Це конкурентність
мережевого очікування, а не паралельне виконання Python-коду.

Глобальний семафор обмежує загальну кількість запитів, семафор
на origin — навантаження на конкретний сервер. Пауза між стартами
обмежує швидкість запитів. Перед зверненням краулер перевіряє
robots.txt, нормалізує URL і використовує множину seen.
Тому повторні посилання не породжують новий обхід, а переходи
на сторонні сайти не дозволені.

Якщо сервер відповідає 429, 5xx або є таймаут, програма може
повторити запит не більше трьох разів із backoff і jitter.
Retry-After задає мінімальний час очікування. Сервер демонстрації
один раз повертає 429, після чого сторінка успішно завантажується.
Усі спроби записуються в crawl.log. Інші 4xx не повторюються.

Краулер — асинхронний генератор: сторінки передаються по одній
у JSONL, без накопичення всього корпусу. Файловий запис та
HTML-парсинг віддаються через asyncio.to_thread. При досягненні
max_pages воркери скасовуються, клієнт закривається. Індексація
запускається окремо, бо токенізація — CPU-bound робота, яка
зупинила б event loop, якщо виконувати її всередині корутини.

Для порівняння запускаю той самий сайт і 200 сторінок з concurrency
1, 5 і 20. Per-host=10 лишається незмінним, тому 20 воркерів
не означають 20 одночасних HTTP-запитів до одного сервера.
У таблиці показую wall time, pages/s, остаточні помилки і
peak RSS. Лог також містить контрольований збій і debug warnings.
Реальні числові результати додаються після запуску на Windows.

## Reflection — короткі відповіді

**1. Що відбувається при await читання сокета?** Корутина віддає
керування event loop. ОС повідомляє про готовність сокета,
і цикл поновлює задачу, коли вона може продовжитися.

**2. Чим cooperative відрізняється від preemptive?**
Asyncio перемикає задачі на await; потоки можуть перемикатися
планувальником ОС. Між await код одного loop не переривається
іншими корутинами, але інваріанти через await потребують Lock.

**3. Чому time.sleep поганий?** Він блокує потік event loop,
і всі інші задачі чекають. asyncio.sleep віддає керування.

**4. Що повертає виклик async def?** Об'єкт корутини, а не
готовий результат. Виконання починається при await або створенні task.

**5. TaskGroup vs gather?** TaskGroup забезпечує структуровану
конкурентність: виняток задачі скасовує решту, група очікує
завершення всіх і повідомляє помилки ExceptionGroup.

**6. Чому краулер масштабується, а потоки лаби 5 — ні?**
Краулер переважно очікує I/O. Токенізація переважно виконує
Python-байткод; звичайний GIL обмежує паралельні обчислення.

**7. Що таке CancelledError?** Сигнал скасування задачі, нащадок
BaseException; не слід його поглинати. finally очищає ресурси.

**8. Навіщо два семафори?** Глобальний захищає ресурси клієнта,
per-host — конкретний сервер. Retry-After відкладає повтор
щонайменше на вказаний сервером час.

**9. Де виконувати CPU-роботу?** Після crawl або у процесному
пулі. asyncio.to_thread придатний для блокувального I/O,
але не є універсальним способом прискорити CPU-bound Python.
