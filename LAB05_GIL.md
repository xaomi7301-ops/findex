# Лабораторна №5 — GIL, потоки, процеси і закон Амдала

## Пояснення своїми словами

У п'ятій лабораторній я порівнюю три способи виконати **ту саму індексацію**
на **тому самому корпусі** документації Python 3.13. Кожен воркер отримує
лише шляхи до файлів та наперед призначені ідентифікатори документів.
Він сам читає файли, токенізує їх та збирає локальний словник. Батьківський
процес об'єднує результати, тому остаточний індекс не залежить від
порядку завершення потоків чи процесів.

### 1. Чому потоки зі звичайним GIL не обов'язково прискорюють роботу

GIL (Global Interpreter Lock) — механізм традиційного CPython, який
дозволяє лише одному потоку в інтерпретаторі виконувати Python-байткод
в певний момент. Це не означає, що Python не підтримує потоки.
Поки один потік чекає файлу або мережі, інший може працювати.
Але токенізація, підрахунок частоти слів, словники й сортування — це
переважно CPU-bound операції. Кілька потоків з активним GIL
здебільшого не можуть виконувати такий байткод паралельно, тому
виграшу може не бути, а перемикання потоків додає витрати.

GIL **не робить прикладну логіку потокобезпечною**. У виразі
counter[key] += 1 є окремі етапи: прочитати старе, додати одиницю
і записати нове. Два потоки можуть обидва прочитати однакове
значення та втратити одне з оновлень, особливо якщо між діями
можливе перемикання. Для спільного лічильника потрібен Lock.
У findex я усунув саму причину гонки: кожен воркер має **власний**
Counter і власні постінги, а об'єднання виконується послідовно.
Отже, жоден воркер не змінює структури іншого воркера.

### 2. Чому процеси можуть прискорити роботу і якою ціною

ProcessPoolExecutor запускає кілька незалежних інтерпретаторів,
кожен із власним GIL. Вони можуть виконувати Python-обчислення
на кількох ядрах одночасно. Однак їх потрібно запустити, створити
окремі адресні простори, передати завдання й результати через pickle.
Тому я передаю **шляхи**, а не великі рядки із вмістом документів.
На зворотному шляху передаються часткові індекси, отже вартість
серіалізації все одно присутня. На Windows я використовую spawn:
функція build_partial оголошена на рівні модуля і доступна для імпорту.

Для порівняння потрібні **wall time** (реальний час на годиннику),
**CPU time** (сукупна робота процесора), **parent peak RSS** і
**merge time**. Час CPU у процесів може бути більшим за wall time:
кілька ядер виконують роботу паралельно. У нашій програмі для
процесів CPU time — це час батька плюс час обчислень воркерів;
CPU, витрачений ними на запуск та пакування результатів, може
бути врахований не повністю. Peak RSS вимірюється **лише для
батьківського процесу**, а не сума пам'яті всіх дочірніх процесів.

### 3. Закон Амдала: чому прискорення перестає рости

Закон Амдала описує обмеження паралельного коду:

S(N) = 1 / ((1 - p) + p / N),

де p — частина роботи, яку можна паралелити, N — кількість воркерів.
Якщо 15% часу послідовні, навіть нескінченна кількість ядер не
дасть понад 1 / 0.15 ≈ **6.67×**. У моєму індексаторі частина,
яка не розподіляється між воркерами, — це merge: зібрати всі
часткові словники, об'єднати та впорядкувати постінги. Саме
тому я вимірюю merge окремо. Далі можуть обмежувати швидкість
pickle, пропускна здатність пам'яті та диска.

### 4. Free-threaded Python 3.13t і безпека

У Python 3.13 є експериментальна збірка без GIL (через
uv python install 3.13t). Вона дозволяє потокам виконувати
Python-код паралельно, але накладні витрати та вимоги до
потокобезпечності залишаються. На кожному запуску я виводжу
**sys._is_gil_enabled()**. Якщо там True, експеримент не можна
назвати «без GIL», навіть якщо виконуваний файл має назву 3.13t:
деякі несумісні розширення можуть знову ввімкнути блокування.

Я не припускаю заздалегідь, що потоки 3.13t будуть швидші:
це перевіряється тільки часом на моєму комп'ютері. Якщо гонки
у тестах не виникнуть, це пояснюється тим, що воркери не ділять
мутабельний Counter. Якби я все ж використовував спільний Counter,
довелось би захищати оновлення через Lock або перейти назад на
локальні словники з послідовним merge.

### 5. Чим I/O-bound відрізняється від CPU-bound

Коли програма чекає на диск або мережу, потоки можуть
перекривати очікування навіть зі звичайним GIL. Коли
переважна частина часу витрачається на підрахунок токенів,
словники й Python-обчислення, допомагає справжній паралелізм.
Вибір між serial, threads і processes у CLI слід робити
після реальних вимірювань, а не просто за кількістю ядер.
