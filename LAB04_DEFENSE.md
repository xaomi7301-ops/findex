# Лабораторна №4 — текст для захисту

**Тема:** Типи, тести, пакування та CLI.

## Виступ (приблизно 5 хвилин)

У четвертій лабораторній я продовжив пошукову систему findex, яку
поступово створював у попередніх лабораторних. Тепер мета — перетворити
проєкт із набору Python-модулів на повноцінний інструмент, який можна
встановити та запустити командою findex з будь-якої папки.

Спочатку я додав типізацію публічних функцій і статичну перевірку
pyright у суворому режимі. Для параметрів із фіксованим набором
значень використовую Literal, генератори повертають Iterator,
а ранжувальники BM25 і TfIdf задовольняють протокол Scorer без
спільного базового класу. Так статична перевірка знаходить помилки
типів ще до виконання коду.

Далі розширив набір тестів. Pytest перевіряє Unicode-токенізацію,
побудову індексу, логічні операції, дерево запиту, скорери,
збереження і завантаження. CliRunner запускає команди інструмента,
а Hypothesis генерує різні випадкові входи та перевіряє загальні
властивості: merge збігається з set, постінги впорядковані,
а збережений індекс можна завантажити без зміни результатів.

У pyproject.toml описані метадані пакета, версія 0.4.0,
залежності Typer і Rich, група dev і точка входу:
findex = "findex.cli:app". Після встановлення wheel користувач
викликає findex index, findex search або findex stats.

Підкоманда index будує індекс із прогресом Rich.
Підкоманда search показує таблицю ранжованих результатів BM25
або TF-IDF. У режимі --json дані друкуються окремими JSON-рядками
в stdout для подальшої обробки. Логи й прогрес ідуть у stderr,
а перемикачі -v та -vv задають деталізацію діагностики.

CI на GitHub запускає синхронізацію uv, Ruff, pyright, pytest
із покриттям, збірку wheel і перевірку інсталяції.
Реліз із тегом v0.4.0 повинен містити wheel для повторного
встановлення. Для здачі лабораторної використовується тег lab-04.

## Команди для демонстрації

Після того як код пройшов усі перевірки:

```powershell
uv sync
uv run ruff check .
uv run ruff format --check .
uv run pyright
uv run pytest --cov=findex --cov-report=term-missing
uv tool install . --force
findex --help
findex index data/python_docs --out index.bin --positions
findex search index.bin "python OR asyncio" --corpus data/python_docs --k 5
findex search index.bin "python" --json --k 2 > results.jsonl
findex stats index.bin
uv build
```

## Reflection — відповіді

**1. Хто перевіряє анотації?** CPython не забезпечує типобезпеку
сам по собі; статичні типи перевіряють pyright/Pylance, а
підказки використовують IDE, Typer та фреймворки, зокрема FastAPI.

**2. Narrowing?** Якщо x: str | None, не можна одразу викликати x.upper().
Після if x is None: return перевіряч звужує тип до str.

**3. Iterator та Iterable?** Iterable дозволяє перебір у for,
Iterator додатково підтримує next(). Функція може приймати Iterable,
але генератор точніше анотувати як Iterator.

**4. Protocol?** Структурний контракт описує потрібні методи.
BM25 і TfIdf мають score(...) з відповідним підписом, тому
pyright сприймає їх як Scorer без наслідування.

**5. Fixture scope?** Фікстура function створюється для кожного тесту;
session — одна на всю сесію. Якщо тест змінить об'єкт сесійної
фікстури, може зіпсувати умови для інших тестів.

**6. Властивість Hypothesis?** Для відсортованих унікальних A і B
merge_and(A,B) == sorted(set(A)&set(B)). Hypothesis генерує багато
різних списків, а під час помилки зменшує контрприклад до мінімального.

**7. Навіщо src/?** При запуску тестів імпортується встановлений пакет,
а не випадково знайдений модуль із кореня репозиторію.

**8. Що робить [project.scripts]?** Під час встановлення створюється
виконуваний командний wrapper, який імпортує findex.cli:app.

**9. Чому logging з %d?** log.info("n=%d", n) відкладає форматування
до моменту, коли рівень INFO увімкнений. f-рядок форматується завжди.

**10. Чому --json не змішуємо з логами?** JSON має залишитися придатним
для парсера. Логи передаємо в stderr, а JSON Lines — у stdout.
