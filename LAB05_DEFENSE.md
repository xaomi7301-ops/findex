# Лабораторна №5 — підготовка до захисту (5 хвилин)

**Тема:** Конкурентність та GIL: потоки, процеси і паралельна індексація.
**Проєкт:** findex, корпус документації Python із попередніх лабораторних.

## Текст виступу (своїми словами)

У лабораторній №5 я продовжив проєкт findex. Раніше індекс будувався
послідовно на одному ядрі. Тепер я порівнюю три виконавці — serial,
threads та processes — на тих самих файлах.

Для цього розділив індексацію на build_partial і merge. Кожен воркер
отримує список шляхів та свій діапазон числових doc_id. Він сам
читає файли, формує Counter та часткові списки постінгів. Після
завершення всі часткові індекси об'єднуються послідовно. Тести
перевіряють, що кінцевий індекс однаковий для всіх режимів, а
також збігається зі старою збіркою з лабораторної №4.

При багатопоточному варіанті ThreadPoolExecutor працює в одному
процесі та спільному адресному просторі. У звичайному CPython
GIL переважно не дозволяє потокам одночасно виконувати чистий
Python-код, тому на CPU-bound токенізації додаткові потоки можуть
не дати прискорення. Натомість ProcessPoolExecutor запускає кілька
окремих інтерпретаторів зі своїми GIL. Процеси справді можуть
використовувати кілька ядер, але платять за старт і передачу
часткових індексів через pickle.

Я вимірюю wall time, CPU time, пікову RSS-пам'ять батьківського
процесу та час merge. Для кожної конфігурації виконую мінімум
три повтори й беру медіану. На графіку відображаю прискорення
відносно послідовної збірки та ідеальну пряму лінію. Закон Амдала
пояснює, чому прискорення обмежене: частина merge залишається
послідовною. Результати потрібно аналізувати за реальними числами,
а не стверджувати, що певний виконавець завжди найшвидший.

Окремо встановлюю Python 3.13t та повторюю вимірювання потоків.
Виводжу sys._is_gil_enabled() і вважаю експеримент дійсно
free-threaded лише коли його значення False. Я не використовую
спільний Counter: кожен воркер накопичує дані окремо, тому
не залежу від випадкового захисту GIL. У спільній структурі
знадобився б Lock.

На GitHub зберігаю код, тести, таблицю вимірювань, PNG-графік
та пояснення LAB05_GIL.md. Після перевірок створюю тег lab-05.

## Команди для демонстрації

У Windows PowerShell (у папці C:\Bag\findex):

    git pull --ff-only origin main
    uv sync
    uv run pytest -q
    uv run pyright
    uv run ruff check .
    findex index data/python_docs --out index-lab05.bin --workers 4 --executor processes
    findex search index-lab05.bin "python OR asyncio" --k 5

Вимірювання (мінімум три повтори):

    uv run python -m findex.lab05_benchmark run data/python_docs --repeats 3 --out benchmarks/lab05-results.json

Free-threaded Python (після встановлення):

    uv python install 3.13t
    uv run --python 3.13t python -m findex.lab05_benchmark run data/python_docs --executors serial,threads --repeats 3 --append --out benchmarks/lab05-results.json

Графік:

    uv run python -m findex.lab05_benchmark plot benchmarks/lab05-results.json --out benchmarks/lab05-speedup.png

## Reflection — короткі відповіді

**1. Що блокує GIL?** У звичайній збірці CPython лише один потік
на інтерпретатор може одночасно виконувати Python-байткод. Він
не блокує всі потоки і не гарантує правильності наших інваріантів.

**2. Чому threads не прискорили CPU-bound індексацію?**
Через конкуренцію за GIL чистий Python-код не працює паралельно;
до цього додаються витрати перемикання. Проте результат залежить
від частки I/O та C-розширень, що відпускають GIL.

**3. Чому processes можуть бути швидші, але CPU time більший?**
Окремі процеси займають кілька ядер одночасно. CPU time може
підсумовувати їхню роботу, а wall time — тривалість на годиннику.
За паралелізм сплачуємо стартом, RAM та серіалізацією pickle.

**4. Чому воркер — функція рівня модуля?** Spawn запускає свіжий
інтерпретатор та імпортує функцію за модулем і назвою. Локальна
функція або lambda зазвичай не підходить для стандартного pickle.

**5. Що відрізняє spawn від fork?** Spawn створює новий Python,
працює на Windows і безпечніший щодо активних потоків. Fork
копіює стан процесу, але успадковані блокування можуть зробити
його небезпечним у багатопоточному застосунку.

**6. Закон Амдала?** S(N) = 1 / ((1-p) + p/N). Якщо 15% часу
послідовні, максимальне прискорення ≈ 6.67× незалежно від ядер.

**7. Чому 3.13t може виявити гонку?** Потоки можуть одночасно
міняти спільний стан без звичайного GIL. Кілька інструкцій
читання-запису не стають атомарними. Рішення — Lock або
ізоляція даних воркерів і merge після завершення.

**8. Приклади задач:** threads — очікування мережі/диска;
processes — CPU-bound Python-токенізація; asyncio (лаба №6) —
багато незалежних асинхронних мережевих запитів.
